# 评分与升级规则

## 评分证据

客户报告可以作为评分证据，但理由必须注明来源，不能据此声称系统已核实。
一个维度未知不影响另一个维度独立评分。
证据不足以区分候选分值时返回 null，不取平均、不默认 3 分、不以未知为低风险。

## 影响 impact

| 分值 | 证据锚点 |
|---|---|
| 1 | 单个用户的非核心功能问题，或明确属于无业务阻塞的一般咨询 |
| 2 | 少量用户轻微受影响，核心业务可继续 |
| 3 | 部分用户或一个部门业务受阻，且有可用替代方案 |
| 4 | 部门或更大范围核心业务受阻，且明确没有可用替代方案 |
| 5 | 全面故障，或明确报告实际数据丢失、账号失陷、敏感数据泄露等严重后果 |

业务影响优先于人数。类别名称不能代替后果证据。
“整个部门无法登录”但核心业务和替代方案未知，不足以在 3 与 4 之间选择，impact=null。
“疑似能看到别人的资料”但数据类型和真实性未知，可先 impact=null，同时立即升级核实；不要为了升级强行给 5 分。
明确报告正在泄露敏感数据时可 impact=5，注明基于客户报告、待核实。

## 紧急 urgency

| 分值 | 证据锚点 |
|---|---|
| 1 | 明确不紧急，可正常排期 |
| 2 | 明确希望尽快，但无具体期限或当前阻塞描述 |
| 3 | 有明确近期期限，且有依据判断并非迫近或严重阻塞 |
| 4 | 明确当前严重阻塞，或业务截止时间迫近 |
| 5 | 正在发生的生产事故、持续泄露或损失，需要立即遏制 |

没有时间或阻塞信息时为 null；不能因没提期限直接给 1 或 2 分。
情绪强烈不独立构成高分证据。相对时间需结合工单时间和时区；无法确定是否迫近时为 null，并询问完整时间。
参考工单发生时的上下文，不把历史事故自动当作当前事故；是否仍持续未知时列为待核实。

## 业务优先级

两个维度都有分值时：
priority_score = impact × urgency，16–25 为 high，6–15 为 medium，1–5 为 low。
任一维度为 null 时，priority_score 与 priority 均为 null，不回填默认分。

## 人工升级 escalation

按以下顺序选择，与业务分数独立：

| level | 条件 |
|---|---|
| immediate | 疑似当前存在越权、账号失陷、泄露、持续数据损失或严重生产事故，需要立即人工核实 |
| normal | 需要人工跟进、补充信息、退款审批、确认产品行为或评估修复，但没有立即升级的证据 |
| none | 现有可靠资料足以回答，无需额外人工操作或核实 |

若报告可能仍在发生的严重风险，持续状态未知不能阻止 immediate，应优先核实是否仍持续。
已明确结束的历史事件按剩余风险和待办判断，不因出现“泄露”等词一律 immediate。
immediate 表示建议立即人工核实，不表示已升级，也不证明事故成立。
一般合规咨询、历史事故说明、情绪激动、未知分数本身均不自动触发 immediate。

## 边界案例

| 输入要点 | 预期判断 |
|---|---|
| 一个人的帮助图标颜色异常，不影响使用，不着急 | impact=1，urgency=1，score=1，low；需要确认产品行为则 normal |
| 部门无法登录，无业务影响、替代方案和时间说明 | impact=null，urgency=null，score=null，priority=null；normal，先补信息 |
| 疑似能打开其他客户资料，范围和数据类型不明 | impact=null，urgency=null；immediate，先核实并评估隔离措施 |
| 客户报告所有生产服务现已不可用且无法开展业务 | impact=5，urgency=5，score=25，high；immediate，注明来源未核实 |
| 只写“紧急，快处理”，没有问题现象 | 不足以形成有意义的工单，先请求现象和影响，不伪造评分 |
